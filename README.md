## Задача 2

Выберите один из вариантов платформы в зависимости от задачи. Здесь нет однозначно верного ответа так как все зависит от конкретных условий: финансирование, компетенции специалистов, удобство использования, надежность, требования ИБ и законодательства, фазы луны.

Тип платформы:

- физические сервера;
- паравиртуализация;
- виртуализация уровня ОС;

Задачи:

- высоконагруженная база данных MySql, критичная к отказу;
- различные web-приложения;
- Windows-системы для использования бухгалтерским отделом;
- системы, выполняющие высокопроизводительные расчёты на GPU.

Объясните критерии выбора платформы в каждом случае.

## Решение 2

1. **Высоконагруженная MySQL, критичная к отказу**  
-->> **Физические серверы (или паравиртуализация с прямым доступом к железу).**  
Критерии: _Низкая задержка I/O, отсутствие «шумных соседей», предсказуемый кэш CPU. Отказоустойчивость — через репликацию и keepalived, а не через гипервизор._

2. **Различные web-приложения**  
-->> **Виртуализация уровня ОС (контейнеры, Docker).**  
Критерии: _Быстрый деплой, горизонтальное масштабирование, эффективное использование ресурсов. Разные приложения изолированы, но легковесны._

3. **Windows-системы для бухгалтерии**  
-->> **Паравиртуализация (KVM, Hyper-V, ESXi).**  
Критерии: _Удобство бэкапов, live-миграция, аппаратная совместимость с гостевыми Windows. Бухгалтерия не прощает простоев, но и не требует сырого железа._

4. **Высокопроизводительные расчёты на GPU**  
-->> **Физические серверы.**  
Критерии: _Прямой доступ к GPU, без прослойки, минимум латентности памяти. Виртуализация уровня ОС отпадает (нет GPU-контейнеров без проброса)._

## Задача 3

Выберите подходящую систему управления виртуализацией для предложенного сценария. Опишите ваш выбор.

Сценарии:

1. 100 виртуальных машин на базе Linux и Windows, общие задачи, нет особых требований. Преимущественно Windows based-инфраструктура, требуется реализация программных балансировщиков нагрузки, репликации данных и автоматизированного механизма создания резервных копий.
2. Требуется наиболее производительное бесплатное open source-решение для виртуализации небольшой (20-30 серверов) инфраструктуры на базе Linux и Windows виртуальных машин.
3. Необходимо бесплатное, максимально совместимое и производительное решение для виртуализации Windows-инфраструктуры.
4. Необходимо рабочее окружение для тестирования программного продукта на нескольких дистрибутивах Linux.

## Решение 3

| Сценарий | Выбор | Ключевое преимущество |
|----------|-------|------------------------|
| 100 ВМ, Windows, бэкапы/балансировка | **Hyper-V** | Встроенные сервисы управления |
| 20-30 серверов, open source, макс. производительность | **KVM** | Скорость + бесплатно |
| Бесплатно, Windows-инфраструктура | **Hyper-V Server** | Родная совместимость |
| Тестирование Linux-дистрибутивов | **VirtualBox** | Простота и портативность |

## Задача 4

Опишите возможные проблемы и недостатки гетерогенной среды виртуализации (использования нескольких систем управления виртуализацией одновременно) и что необходимо сделать для минимизации этих рисков и проблем. Если бы у вас был выбор, создавали бы вы гетерогенную среду или нет?

## Решение 4

Гетерогенная среда — это когда у и VMware, и Hyper-V, и может ещё KVM по мелочи. Звучит мощно, но на деле — головная боль.

Проблемы начинаются сразу: у каждой системы своя консоль, свои кнопки, свои баги. Чтобы перенести виртуалку с одной на другую — надо её выключить, сконвертировать диск, помолиться. Живой миграции нет. Бэкапы — отдельная песня, для каждой платформы своя система. Мониторинг — то же самое. Плюс админы должны знать всё и сразу, а такие люди дорогие и редкие.

Если уж так вышло, что две платформы есть (например, купили Hyper-V), то чтобы не взорвалось: общее хранилище, сверху Ansible или Terraform, бэкапы централизуешь (Veeam, например), и строго делишь задачи: на этой — Windows и бухгалтерия, на той — Linux и тяжёлые базы. Без пересечений.

А вообще, если есть выбор... Одна нормальная платформа, которая закрывает 90% потребностей, лучше, чем две, каждая со своим характером. Гетерогенность — это не фича, это legacy или вынужденная мера. Исключение — если тестируешь что-то новое или железо специфичное. А так — не надо себе придумывать лишнюю работу.
